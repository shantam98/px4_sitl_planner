# InspectBot — Project Overview

## 1. Introduction

InspectBot represents a paradigm shift in embodied AI for hazardous industrial environments, delivering an edge-native, multi-modal robotics platform designed to automate complex inspections. The deployment of autonomous Unmanned Aerial Vehicles (UAVs) for industrial inspection is currently limited by a reliance on dense geometric mapping. While effective for basic navigation, these systems lack semantic understanding, the ability to recognize specific industrial assets, and rapidly exhaust the compute constraints of edge devices.

This Master's project, developed for the Intelligent Robotics Systems program at the National University of Singapore (NUS-ISS), introduces InspectBot: a cognitive, edge-native UAV architecture designed for the NVIDIA Jetson Orin Nano. InspectBot solves these limitations by shifting the navigation paradigm from heavy volumetric mapping to a lightweight, sparse semantic topological graph memory layer using VLM and SLAM, low-cost dynamic obstacle avoidance, user-guided VLM-based exploration, and autonomous landing on uneven ground. We focus more on the innovation of the key internal layers of the drone than on the overall system integration.

## 2. Architecture at a Glance

InspectBot is organised as four asynchronous layers that communicate through ROS 2 topics. Each layer is independently testable and replaceable. The diagram in the project root (`architecture.png`) shows the full message flow; the layers in summary:

- **Layer 1 — Cognitive Goal Management & Exploration.** Receives natural-language instructions from the human operator. An LLM-based intent router classifies each instruction into *Analyse*, *Exploit* (target is in the semantic memory), or *Explore* (target is unknown). Unknown targets are handed to the VLM Spatial Grounding module for zero-shot localisation from the live camera view.
- **Layer 2 — Semantic Perception & Topological Memory.** cuVSLAM provides hardware-accelerated visual-inertial odometry (`map → odom`). NanoOWL performs open-vocabulary 2D detection on the live RGB stream. The Semantic Graph Combiner fuses NanoOWL bounding boxes with cuVSLAM pose to produce 3D landmark positions, which are persisted in a Redis JSON graph keyed by label.
- **Layer 3 — High-Frequency Local Dynamic Planner.** A 20 Hz reactive planner consuming a 360° point cloud (5× MaixSense ToFs merged in `base_link`). For each cycle, ~1000 Motion Primitive arcs are evaluated against the live cloud and a goal direction; the best valid arc's initial tangent is published as the velocity setpoint. No global map is required.
- **Layer 4 — Failsafe & Flight Control Interface.** A `cmd_vel` mux / FSM arbitrates between the local planner's nominal trajectory and the emergency-landing module's failsafe trajectory. The chosen velocity is translated to PX4 trajectory setpoints and pushed over the MicroXRCE-DDS bridge to the Pixhawk flight controller. Telemetry watchdogs (battery, signal, VSLAM tracking state) feed an emergency trigger directly into the mux.

The boundaries are deliberate: Layer 1 owns the *what*, Layer 2 owns the *where*, Layer 3 owns the *how*, and Layer 4 owns the *guarantee*.

## 3. System Overview and Industrial Use Case

To fully realise the InspectBot's edge-native capabilities, the four distinct architectural layers do not operate in isolation; rather, they form a continuous, asynchronous pipeline bridging high-level cognitive reasoning with low-level deterministic flight control.

This multi-layered approach is best illustrated through a practical industrial inspection scenario: **autonomous monitoring of an offshore oil rig's pressure systems**.

### Step 1 — Cognitive Goal Management & Exploration (The Intent)

An operator issues a natural language command: *"Inspect the main cooling valve for corrosion."* The Large Language Model (LLM) intent router processes this command, recognizing it as an **Explore** objective since the exact coordinates of the "main cooling valve" are not yet known.

### Step 2 — Semantic Perception & Topological Memory (The Cognition)

As the UAV traverses the rig, the NanoOWL vision-language model actively scans the environment looking for visual matches to the prompt *"main cooling valve."* Once detected, the Semantic Graph Combiner synchronizes this 2D pixel detection with the high-speed spatial odometry generated by cuVSLAM. The result is a precise 3D coordinate `(X, Y, Z)` representing the valve, which is immediately committed to the persistent Redis database as a semantic node.

### Step 3 — High-Frequency Local Dynamic Planner (The Navigation)

With the semantic layer providing the overarching global waypoint for the valve, the local dynamic planner takes over the immediate flight path. Operating at 20 Hz, this layer evaluates real-time depth data from the onboard Time-of-Flight (ToF) sensors against a library of Motion Primitives. It smoothly routes the UAV around dynamic physical obstacles, such as temporary scaffolding or moving personnel, ensuring collision-free traversal toward the cognitive objective.

### Step 4 — Failsafe & Flight Control Interface (The Guarantee)

Throughout this entire mission, the Failsafe Finite State Machine (FSM) continuously arbitrates the velocity commands sent to the PX4 flight controller. If the UAV encounters a critical signal loss deep within the rig's metallic infrastructure, the FSM immediately overrides the cognitive and planning layers, utilizing a downward-facing depth sensor to execute an autonomous, terrain-aware emergency landing.

## 4. Key Challenges

### Implementation and Debugging

This project was very challenging as debugging a certain behaviour of our required algorithm would require monitoring the behavior of multiple topics and nodes at the same time. This is the key motivation for our future work to fine-tune and improve each component towards its desired behavior.

### Simulation Challenges

Running simulation with reliable results has been a key challenge towards fine-tuning and testing. The system configuration present within the entire team was incapable of running PX4-SITL combined physics-based simulation in Gazebo. This was our baseline, since it is the most widely accepted simulation format for UAVs.

Even after moving to a more advanced system like the NUS Vanda Cluster with A40 GPUs — on which we spent 3 days of configuration time — the results had a different characteristic due to lag introduced by the virtual machine. However, using ROS bags and analysing results locally helped with the situation. Moving forward, this is a preferred setting to run any ablation and testing of our system combined.

### Hardware Challenges

For first timers, working on hardware is always a challenge. But it was equally rewarding and fun. We learned soldering, system connection protocols, protocols for UAV systems, electronics, systems thinking for drones, Pixhawk, PX4, ArduPilot, Ground Control, NVIDIA documentation for Isaac ROS, Isaac Sim, Jetson, working on edge-computing devices, and mechanical design with 3D printing. While it was a great learning curve, we faced many failures in multiple aspects of these challenges, and hence hardware tuning is one of the main avenues for future work.

### Software Integration

This is another key aspect of our future work. Given the restricted time frame and ambitious scope of the project, we focused on novel implementations and on enhancing the performance of the key modules. While the way we work makes it easy to integrate our individual contributions, testing and debugging the entire system is an extremely tall task due to the complexity of the system and the number of nodes/topics to track. System integration followed by deployment would be an immediate win for our system and would potentially make this project more marketable and SOTA.
